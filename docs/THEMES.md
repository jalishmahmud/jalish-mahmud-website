# Design and color modes

The site has two independent preferences:

| Preference | Values | Default | Storage key | HTML attribute |
| --- | --- | --- | --- | --- |
| Design | `classic`, `v2` | `classic` | `design` | `data-design` on `<html>` |
| Color | `dark`, `light` | `dark` | `theme` | `data-theme` on `<html>` |

The buttons in `components/ThemeToggle/ThemeToggle.js` sit beside each other in the header. Each updates only its own preference. `localStorage` persists both values; if storage is unavailable, the controls still work for the current page. The initial server HTML always uses Classic Dark, so public routes remain static or dynamic exactly as they were before this feature. No route reads a theme cookie.

## Rendering and loading

`app/layout.js` puts a small inline script in `<head>`. It reads both saved values while the browser parses the HTML and sets the root attributes before paint. The root element has `suppressHydrationWarning` because the script may change those attributes before React hydrates. The controls use `useSyncExternalStore` with the server defaults, so their initial markup matches the server and then updates to the saved values without a hydration mismatch.

Classic uses the existing CSS Modules and `app/globals.css`. Components add stable classes through `lib/design-styles.js`; the same JSX, server components, data calls, routes, metadata, and structured data are used for either design. V2 rules are scoped under `html[data-design="v2"]` in `public/design-v2.css`. The V2 generator drops only `font-size`, `line-height`, and `font` declarations; its layout, decoration, animation, gradients, and other styling remain intact. Both designs use the Classic font size and line height at every breakpoint. A Classic visit never requests the V2 file. A saved V2 visit requests it immediately from the head script; the page remains hidden until it finishes loading, avoiding a design flash or visible layout shift. Switching to V2 waits for the stylesheet before changing the root attribute. Switching back uses the already loaded CSS without another request. A stylesheet error falls back to Classic.

The V2 sheet is about 10 KB gzipped. There is one shared set of components, dependencies, assets, and blog queries. Gallery from V2 is rendered in both designs, so the page content and navigation stay the same for people and crawlers. The `v1` SEO and blog implementation remains the source of truth: theme choice does not affect URLs, canonicals, metadata, JSON-LD, sitemap, robots, Open Graph, or article data.

## Editing a theme

- Edit Classic CSS in its existing CSS Module or `app/globals.css`.
- Edit V2 CSS in `styles/v2-source/*.css`, then run `npm run build:design`. The generated `public/design-v2.css` is committed and also regenerated by `npm run build`. Each V2 source module corresponds to the existing component CSS Module; global rules go in `styles/v2-source/globals.css`.
- Font size and line height are controlled by Classic CSS Modules across the site. The V2 generator discards those declarations, including the `font` shorthand, so edit Classic CSS when changing the shared type scale.
- The Technical Expertise grid inherits its column count from the Classic Skills CSS Module: two columns on desktop and one on mobile. Keep `grid-template-columns` out of `styles/v2-source/Skills.css`.
- Section spacing uses 40px padding per side on desktop and 25px on mobile, giving at most 80px and 50px between adjacent sections. Hero bottom padding, blog featured spacing, page bottoms, and footer top spacing follow the same budget; header clearance at the top of a page stays separate.
- For a new component with different V2 styling, wrap its CSS Module mapping with `withDesignStyles(baseStyles, "ComponentName")`, add a matching V2 source file and its namespace to `scripts/build-v2-design.mjs`, then regenerate the sheet. Keep the namespace unique. A CSS Module class such as `styles.card` becomes the existing hashed class plus `design-ComponentName-card`; the generator translates V2 selectors to that stable hook.
- Add design independent content and behavior to the shared component. Avoid branching on design in server rendering. Add color values as CSS variables for each design and color mode. Keep V2 selectors under its root scope.
- If preference names or the V2 stylesheet URL change, update `lib/theme-preferences.js` and `lib/theme-bootstrap.js` together.

V2 source CSS is a snapshot of the visual styles from the `v2` branch. The branch's changes to SEO, blog data handling, editor behavior, and copy were not merged into the theme layer because they are unrelated to presentation and would change existing production behavior.

## Verification

Use Node 24 from `.nvmrc` (Next.js requires Node 20.9 or newer). Run `npm run lint`, `npm run build`, then start the production server with `npm run start -- -H 127.0.0.1 -p 3100`. `node tests/theme-browser.mjs` runs headless Chrome against all four combinations at desktop and mobile widths. It checks the active attributes, V2 CSS loading, overflow, duplicate IDs, button names, and toggle persistence. Set `CHROME_PATH` for a nondefault Chrome location, `TEST_ORIGIN` for another local port, or `CAPTURE_DIR` to save screenshots. Verify the contact form and admin workflows separately when those areas are changed; they share the global palette but their behavior is outside this theme layer.
